# 自主群聊 Agent：感知、唤醒与行动循环

状态：设计草案，2026-10-28。本文是目标架构，不代表已经实现或通过实验。

## 目标与现状

群聊 Agent 应持续接收平台实际交付的事件，并在获得计算资源时自主判断该观察、等待、主动参与，还是结束本轮。被 @、被回复和没有 @ 都是上下文信号；它们不直接决定 Agent 必须说话或不能思考。

当前实现不是这样：[GroupAgent](../../app/bot.py) 先调用 [ParticipationPolicy](../../app/policy.py)，静默时不会启动模型；只有策略决定回复，才把有限历史和当前窗口渲染成提示词。自主参与的固定分数和阈值、提及的强制回复，都是模型调用前的社交决策。消息落库后有可能在较晚的回复中作为历史出现，但落库不等于 Agent 已经看见。

Core 当前的公开文本入口是 `Runtime.submit_text`，固定事件路由和校验不提供任意外部结构化观察入口。`Transcript.project` 也只投影已识别的事件；仅将一个事件写进日志或注册路由不足以保证模型看到它。当前空的模型响应被判为 `response_invalid`，不能直接改称主动沉默。Bot 的每个话题 Runtime 目前使用空工具目录，发言由应用代替模型执行。Core 的 journal 不能单凭现有实现自动恢复会话 transcript。

这些是本轮源码检查的结论，不是新设计的验收结果。此前离线对话实验也不能证明主动参与能力。

## 基本原则

1. **观察先于社交判断。** 每个已授权、实际收到的群聊事件进入对应话题的持久事件流；普通消息和明确提及都能让 Agent 获得判断机会。
2. **调度不是社交裁判。** 合批、计时、公平性、权限和硬预算可以约束何时执行、能否执行，不能用关键词、固定权重或外部分流判断是否值得参与。@ 可以缩短排队时间，但不能强制发言。
3. **一次自主工作单元中决定并行动。** 同一个自主工作单元获得观察、状态和可用能力，选择无动作、等待或调用发言工具。它可以关联多次模型推理与工具往返；不先调用一个外部分类器，再由另一个生成器被动回复。
4. **无动作是正常结果。** Agent 明确结束或等待，与空模型输出、预算耗尽、系统暂停、拒绝执行、网络失败分别记录。
5. **对收到的事件负责，不虚构感知。** Telegram 隐私模式、权限、断线和支持的更新类型决定 Bot 实际收到什么。`received`、`presented`、`processed` 是不同状态；合批、摘要与上下文截断都不能伪装成模型逐条看过原文。
6. **以机器人身份参与。** 自然交流不等于假装真人；用户问及身份时应如实说明。

## 端到端循环

下文的“自主工作单元”是一次获得观察和行动机会的**逻辑单位**，有独立的 `workflow_id`，可以关联一个或多个现有 Core activation、模型调用与工具结果。它不是现有 Core `activation` 的同义词：目前 Core 的 activation 按现有语义处理一次模型请求及其工具调用，不能直接假设多次推理都属于同一个 Core activation。最终由 Core 扩展还是由应用编排，应先以真实最小复现验证工具回执和后续推理，再决定；旧接口与 activation 含义保持兼容。

```text
Telegram 实际交付的更新
  → 授权、去重、持久事件日志       [接收与模型可见性分开]
  → 按 chat/topic 合批并排队        [普通消息也会唤醒；预算与公平调度]
  → 冻结观察范围 + 取状态快照
  → 自主工作单元：观察 → 判断 → 选用工具 → 结束或等待
  → 行动意图与版本校验 → 持久 outbox → 平台执行
  → 完成/失败/未知结果写回事件流   [不等于自动再次发言]
  → 新事件或等待到期触发下一次自主工作单元
```

### 1. 感知：持久事件流

应用适配器按 `(chat_id, topic_id)` 隔离事件，记录稳定的本地递增序号、平台更新 ID、类型、来源、接收时间、平台提供的事件时间及必要的消息/回复/发送者信息。消息正文和用户提供的元数据是观察数据，不是指令或系统权限。

只承诺覆盖应用已授权并实际收到的事件。文本、可处理的媒体说明、消息编辑、@ 与回复、Agent 的发送结果，以及可取得的反馈，可各自作为不同类型；平台未交付的删除等事件不能假装存在。编辑以新的更新事件表示，关联原消息，不能因原 `message_id` 已存在就静默丢弃。反馈继续使用已有的匿名聚合口径，不因为引入事件流而额外保留反应者身份。

摄取和本地接收位置遵守持久一致性：更新去重及内容记录成功后才推进游标。采用有界队列，存储承压或上游拒绝时显式记录和暴露；不能因为进程内任务队列满就静默丢弃已承诺接收的事件。原始事件的保留、清除和隐私策略仍需与应用的现有管理语义一起确定。

### 2. 唤醒：聚合和预算，而不是外部判断

调度器为每个话题维护未处理事件序列。普通消息到达后也开启一个有最长期限的合批窗口；短时突发合并，低频群最后一条消息不会永远留在队列。消息持续不断时，绝对截止时间或事件数上限仍能产生批次。@ 和回复可缩短等待，但最终说不说由 Agent 判断。

参数示意：空闲 2 秒或最长 15 秒触发一次，先到为准；这些数字只是实验起点，不是已经测出的最优配置。用单调时钟衡量运行中的防抖，持久截止时间用可恢复的墙钟表示。定时等待到期、尚未完成的恢复工作也可触发；自身发送回执默认进入后续观察，但不必单独触发，避免对自己反复回应。若 Agent 正在明确等待该回执，可依等待条件唤醒。

同话题保持可解释的处理顺序，其他话题可以在全局并发和每群预算内运行；模型生成期间仍接收新事件。每个 scope 都需要公平调度、最大排队时间或可观测的预算延迟，避免热闹话题永久饿死安静话题。硬预算耗尽时保留待处理事件并记录 `deferred_budget`；管理暂停、安全拒绝、存储压力和超时也有独立状态。它们不计为 Agent 自主沉默。预算可能导致参与过晚，长期资源不足时不能承诺固定唤醒时限。

### 3. 观察与自身状态

一个自主工作单元以已冻结的事件序列范围、当前状态版本、相关上下文、可用工具、预算和限制作为输入。后续到达的事件继续写入日志，进入下一批或在刷新上下文时显式加入，不能被旧批次提交覆盖。

长期状态按话题隔离，至少包括最近参与记录、未决话题、来自群成员的明确偏好、Agent 自己的等待条件、承诺、相关事件引用、有效期和行动结果。状态由 Agent 选择记录并可修订，不把模型猜测直接提升为确定事实；摘要保留来源与不确定性。信息需要有限保留、删除和纠错机制，不能默认无限保存群聊。

上下文由增量事件、适量原文、带来源摘要及状态构造，避免每次把相同的滚动窗口当作新用户消息反复注入。原始事件日志是权威来源，摘要是有损投影：显示压缩范围、缺失或截断，必要时允许 Agent 在预算内读取原文。记录哪些事件的原文或摘要实际进入过模型视图；超出上下文的积压应分段、明确压缩或记录过期，不能宣称每条消息都被模型完整读过。

每个事件或连续范围有覆盖账本：已接收；是否以原文或带来源的摘要纳入某次模型请求；若未纳入则记录原因；以及相关工作单元是否正常结束。这里的“呈现”只表示本地请求实际包含该内容，不证明模型理解它，也不排除服务端自行截断。摘要要记录来源范围与版本，不能把一条摘要等同于逐条原文阅读。只有对应范围已纳入成功完成的工作单元，且其状态和等待已提交，才可推进连续处理位点；模型失败、摘要失败、未呈现或预算延期都保留未处理缺口。因保留期限或管理处置而放弃的事件应单列 `unprocessed_expired` 或其他明确处置，不能改记为自主沉默；即使接收高水位继续向前，缺口账本仍需保留。

Bot 自己的确认消息、其他 Bot 的消息和群成员消息必须保留不同来源，不能把所有 `is_bot` 消息都投影成 Agent 自己的发言。尚未发送、失败及结果未知的生成内容不能被投影为确定的公开群聊事实。

### 4. Agent 决策与行动

下面是能力语义的示例名称，**不是现有 API**：

- `observe` / `read_context`：在权限和上下文预算内读取事件与状态。
- `update_state`：记录、修订或删除带来源和有效期的状态。
- `wait_for_event`：登记对未来事件的等待并结束本轮；等待不占用模型。
- `wait_until`：登记未来重新观察的时间、目的和有效期；到期后重新判断，不是预先授权发送。
- `send_message`：在当前 scope 内提出要发送的内容、可选回复目标和有效期。
- `finish_silently`：正常完成本轮；不产生可见群消息。

无需把 Agent 的内部思考或普通文本自动当作群消息。只有明确的发言工具调用才构成对外行动；工具在同一个自主工作单元中接收意图，适配器检查权限、安全、速率和目标，然后提交 outbox。Agent 可在一个工作单元里阅读、更新状态并决定发送，也可结束而不发言。工具接受意图不代表 Telegram 已送达；异步完成结果可能在工作单元结束后才产生，并以同一行动 ID 关联到后续观察。

工作单元的调度状态为 `running`、`completed`、`deferred` 或 `failed`；其 Agent 结果单独记录为明确沉默、等待及行动的组合。发送并登记后续等待可以同时发生；`finish_silently` 只用于本单元没有提出对外发送行动。`completed` 只说明工作单元正常完成，行动仍以自己的 `pending/sending/sent/failed/unknown` 状态为准。工具拒绝需反馈 Agent 或记录明确失败，不能算作成功沉默；超时和重试耗尽保留未完成原因和恢复路径。等待登记、状态更新与工作单元的处理进度在应用权威库内一起提交。

模型应有明确的 `finish_silently` 或受约束的 `no_action` 正常结果。空输出、无效工具调用、provider 失败和超时仍是错误；不要将它们一律映射为主动沉默。记录简短、可公开的结果类别即可，不要求保存模型内部推理过程。

Agent 不仅可以在未被 @ 时发现未解的问题并补充有效信息，也可在 @ 只是误触、问题已解决或没有回应价值时选择沉默。安全规则拦截与 Agent 主动拒绝在日志中分别归因。

### 5. 等待与延迟参与

等待不保持模型请求常驻。可匹配的结构条件由调度器处理，例如同一话题有新消息、特定行动回执到达、时钟到期。像“问题已经解决”这类需要理解语义的条件，不能暗中交给关键词判断；需要向 Agent 呈现新观察，由它重新判断。

持久等待至少记录 ID、创建时间、触发类型、关联事件或目的、到期时间、最晚有效时间、作用范围及预算。支持取消、替代、过期和重启恢复；为周期性等待设置次数或预算上限。到期后 Agent 看见最新状态，再选择发言、继续等待或取消。预先声明的执行截止时间到期时，调度器可停止执行该条旧意图，但必须记为 `expired_unexecuted` 并留下供 Agent 观察的结果，不能自行判断“已经没有社交价值”或记为 Agent 的沉默。用户明确请求的提醒若已错过，应让 Agent 判断是否仍有价值并如实说明延迟，而不是假装准时。

## 意图、并发与恢复

目标是在可靠性基础上支持新行为模型，而不把外部策略包装成自治：

1. 应用数据库是 durable inbox/outbox 的权威来源；Core 与应用不能假定跨两个独立存储存在单个数据库事务。冻结批次、状态版本、`workflow_id`、Core activation ID 和处理进度都须可恢复。
2. 工具副作用执行之前，先把已收到的模型工具调用、稳定的行动身份和 outbox 意图持久化。可重放已持久化的模型结果，但不能靠重新生成一次模型输出来假装工具调用 ID 必然稳定。若意图已提交，恢复时先核对该行动状态，再决定如何继续；若模型调用中断且尚无行动意图，才可按恢复策略重新运行。
3. 发送领取与当前行动版本、授权、目标、有效期等执行前检查在同一原子操作中完成。生成期间的新事件不应直接用关键词判定社交相关性；需要刷新时，把新事件和执行结果反馈给同一 Agent 工作单元，由 Agent 确认、修改、取消或等待。持续高流量下严格要求“零新事件”可能导致永远无法发言；重评次数、延迟和让出队列必须有界，并作为限制和评测指标，而不是隐藏成静默。
4. 消费位点、处理结果、状态版本和等待登记的提交方式必须防止崩溃后漏观察或覆盖新事件；如果一个工作单元的工具意图先于最终状态落盘，其恢复协议必须能识别并衔接该意图。逐边界崩溃测试是实施要求，不是本文已有证据。
5. 出站区分 `pending`、`sending`、`sent`、明确 `failed` 和 `unknown`。进程在平台接受后、本地确认前退出时，实际送达状态可能无法确定；`unknown` 不盲目重发，也不冒充确定成功或失败。无远端幂等键时不承诺端到端恰好一次。
6. 每一话题的恢复工作与新工作须保证顺序；跨话题有界并发，不能让其他话题取消本话题的行动。第一版仍按单活进程设计，不宣称具备多进程租约。

**执行顺序和恢复契约：**

1. 在应用库冻结观察范围、状态版本及 `workflow_id`。每次模型请求绑定 `core_activation_id` 和步骤号，完成前不改变事件处理位点。
2. 取得模型响应后，在任何带外部副作用的工具执行前，持久化可恢复的模型响应信封和精确工具调用；每个工具调用以已存储的 `(workflow_id, step_id, tool_call_id)` 关联唯一行动 ID。恢复使用已保存的调用，不能重新生成一个看似相同的调用作为幂等依据。现有 Core 工具执行路径不保证这一步，因此需要可验证的通用持久化钩子或等价协议；这是待验证设计，不是当前保证。
3. 在应用库内以唯一键创建或读取同一行动的 outbox 和工具回执；重复提交返回已有记录。状态变更、等待登记按自身操作 ID 幂等落盘。发送 worker 只能读取已持久化的意图，并将版本、授权和有效期校验与 `pending → sending` 原子领取。Core journal 与应用库之间通过稳定 ID 衔接，不声称有跨库事务。
4. 在本地确认发送结果时，原子写行动结果和对应观察事件；工作单元结束时，原子记录终态、状态版本、等待和可推进的连续处理位点。已经写入的行动与状态更新通过唯一键关联，重启可以继续收尾而不重新产生副作用。

| 崩溃前的最近持久状态 | 恢复处理 |
|---|---|
| 只有已冻结工作，尚无模型响应 | 重试或恢复模型调用；此时必须确保此前没有被允许执行的外部副作用。 |
| 模型响应已保存、行动尚未入库 | 读取保存的调用，用同一操作 ID 创建意图；不重新生成模型响应。 |
| `pending` | 按版本、授权和有效期领取或取消，并保留结果；不复制意图。 |
| `sending`，远端可能已接受 | 标为 `unknown`，不自动重发；可用可靠的远端证据或人工对账。 |
| `sent`、`failed`、`unknown` 但工作单元未收尾 | 复用该行动结果，幂等补写回执、状态或工作终态，禁止再次发送同一行动。 |
| 工作单元已完成 | 保留其结果和位点；后续事件属于后续工作单元。 |

**刷新与过期：** 默认只依据序号、事件类型和时间等机械事实判断是否需要刷新，不判断消息“值不值得回复”。发言意图记录 Agent 已观察到的序号、有效期及其选择的新鲜度要求；先以严格模式为默认：同话题有未观察事件就暂不领取发送，返回 `needs_refresh` 并把增量交还 Agent。Agent 也可以明确选择有界模式，接受有限时间或事件数的未观察窗口；执行器施加系统硬上限，字段缺失或无效时回到严格模式。两种模式都在同一事务里检查版本和领取状态，事务完成之后到达的新事件不能追溯性改变已经领取的行动。严格模式在高流量下可能一直冲突；有界模式可能错过刚到的解决信息，不能保证完全避免过时发言。每个工作单元以最多两次刷新作为实验起点；上限或预算耗尽时记录 `deferred_refresh`，保留输入并让出队列，由后续公平调度重试，不能记成主动沉默。该参数和有界模式上限须通过真实延迟、打扰和成本实验确定。

## 逻辑工作单元的延续（continuation）

**状态：已实现（2026-10-29）。** 之前只有 intent：跨激活保存的目标数据，每次唤醒仍然
新建一个 workflow，数据里没有任何东西说明"这两次激活是同一件事"。现在补上了
`workflow_episodes`——逻辑工作单元的持久身份，详见下面的"实现记录"与
`docs/evaluations/continuation-investigation-2026-10-29.md`。

**问题。** 一次 workflow 等于一次模型激活。`wait_for_event` / `wait_until` 只登记了一个
唤醒条件，没有留下"我当时正在做什么"。于是每次唤醒都是重新构造一个短暂的决策任务：
Agent 看到的是新观察 + 一堆状态键，而不是一个持有未完成意图的执行上下文。表现上是
"每隔一段时间被叫醒、重新决定是否说话"，而不是"一直在参与同一场对话"。

**不追求的东西。** 不是让模型常驻运行，也不是无限消耗 token。事件唤醒推理本身是合理的。
要改的只是：唤醒的是**同一个持续存在的逻辑 Agent**。

**最小模型。** 每个 `(chat_id, topic_id)` 至多一条 *active intent*：

```
agent_intents(
  intent_id, chat_id, topic_id,
  goal,            -- 她自己写的："等林贴出日志，看是否还报 Code 62"
  status,          -- open | resolved | abandoned
  opened_at, updated_at,
  expires_at,      -- 兜底，防止陈旧意图永久污染上下文
  resolved_by      -- send_message / wait_satisfied / explicit / expired
)
```

与现有结构的区别：

| | 现在 | 加入 intent 之后 |
| --- | --- | --- |
| 唤醒时看到 | 新观察 + `agent_state` 键值 | 上面这些 **加上** 未完成意图全文 |
| workflow 之间 | 彼此独立 | workflow 记录它运行时的 `intent_id`，可回溯同一逻辑线程 |
| 等待到期 | 只发 timer 事件 | timer 事件带上意图，明确"你上次在等这个" |
| 结束 | workflow 关闭即结束 | 意图可以跨多个 workflow 存活，直到显式解除或过期 |

**不假装它是持久进程。** intent 是**数据**，不是活着的协程。它保证唤醒时上下文连续，
不保证事件顺序之外的任何执行连续性。这一点必须写在实现里，否则又会变成"看起来像
Agent、其实是状态机"。

**解除方式**（都要可观测，不能静默）：

- `resolve_intent`：她自己判断已经不需要继续了；
- `send_message` 里带 `resolves_intent: true`：说完就算完成；
- 到期：记为 `expired`，并在下一次渲染中明确告知，不留悬空；
- 工作单元失败不解除意图——没做成不等于不想做。

**与 `wait_*` 的关系。** 等待回答的是"什么时候再叫我"，intent 回答的是"叫醒我之后我还
在干什么"。两者独立：可以不等待而有未完成意图，也可以等待而无意图。把两者混成一个
字段会让"我只是想晚点看"和"我有件事没做完"无法区分。

### 实现记录：`workflow_episodes`（2026-10-29）

intent 解决了"目标跨激活可见"，但没有解决**身份**：`workflows` 每次都是新的一行，
数据里没有东西说"这两次激活是同一件事"。补的是这一层。

```
workflow_episodes(
  episode_id, chat_id, topic_id,
  state,      -- open | closed
  reason,     -- 关闭原因
  intent_id,  -- 这一轮工作自己声明的目标（可为空）
  opened_at, updated_at, closed_at
)
workflows.episode_id  → 每次激活归属于哪个逻辑工作单元
agent_waits.episode_id → 这次等待是在为哪个工作单元等
```

- **开启/加入是同一个操作**（`open_episode`）。部分唯一索引保证每个 scope 至多一个
  open episode；并发的第二次调用会**采用**赢家的身份，而不是另造一个。
- **模型能看到这是延续。** 渲染的 payload 增加 `episode: {episode_id, opened_at,
  activations, continuation}`；`continuation: true` 表示这次唤醒属于同一件事，而不是
  重新开始判断。日志同样打印 `episode=` 与 `continuation=`。
- **关闭条件是窄的**：只有当没有未完成意图、也没有活跃等待时才关闭。新消息**不算**
  理由——在热闹的群里新消息永远存在，把它当理由会让一个 episode 开好几天，
  "延续"就又失去意义。
- **重启恢复**：`running_workflows` 照旧标记为中断，但 episode **故意保留**。启动时
  先用持久事实核对一遍（还有 open goal 或 active wait 才留下），再打印每个仍在的
  episode 及其已有激活数，这样"中断后继续"和"全新开始"可区分。
- **投递后才关闭目标**：`send_message` 带 `resolves_intent` 时，目标只在这条消息真的
  送达后关闭；并被丢弃的回复不会替她说"已经说完了"。

**仍然只是数据，不是常驻进程。** episode 保证唤醒时身份与上下文连续，不保证事件顺序
之外的执行连续性。

**验证。** `tests/test_episode_continuation.py`（9 项）覆盖：等待/定时器唤醒加入同一
episode、首次激活不是延续、无事可做时关闭、并发开启采用赢家、NULL topic 下唯一性、
送达后关闭目标与 episode、重启后 episode 保留、旧库迁移补列。
`tests/test_episode_restart_leak.py` 补的是**崩在两次写之间**的边界：投递已关掉目标、
episode 还没关，重启后这一行看着像「还在等」。旧实现在这个状态下会把话题里下一句无关的
话渲染成 `continuation`；现在启动时按「是否还有 open goal 或 active wait」重新推导，
无事可做的 episode 直接关闭，再让新观察进来。App 全量 406 passed，跑在本地 Core
`5f65658` 上；`pyproject.toml` 固定的是 `7618bd0`，二者不同，见下文。

## Core 与 Telegram 应用的边界

**Nervipulsa Core 的通用能力候选：**

- 向已有使用方兼容地增加有界的外部观察接入和结构化投影；明确“接收”“呈现给模型”和“唤醒”是三个独立动作，拒绝、背压及容量可观测。是否通过通用注册机制或固定 `external.observation` 信封表达，需用最小复现比较，不先假定新 API 已存在。
- 提供 activation 对输入批次、工具调用和结果的关联；一个批次可包含多个事件。将明确的 `no_action` 作为成功完成，同时保持旧空响应错误语义与旧公开接口。
- 将工具意图接受、异步行动结果和 activation 完成区分；把 `accepted` 与 `completed` 的关联、压缩和重建从 Python 专有实现推广为通用机制。不能把接受行动当成行动已成功。
- 明确新的观察事件对 actor 唤醒、暂停恢复、预算重置和上下文压缩的影响；行动结果的投影与是否唤醒分开配置，防止自激循环。
- 不要求 Core 理解 Telegram 的群、话题、@ 或消息权限。真正需要跨重启持久恢复的契约应单独设计与验证，不能假定当前进程内 transcript 或 journal 已经提供它。

**Telegram 应用负责：** 接收和授权更新、按群/话题隔离、匿名反馈及平台语义；调度与资源预算；映射为观察；提供受限发言工具；outbox 与 Telegram 发送；去重、持久恢复和不确定结果处理。`ParticipationPolicy`、`proactive_score` 和强制 mention 回复退出新路径的社交决策；旧实现只作为离线对照和旧记录兼容材料，不能在新路径失败时悄悄作为自治兜底。

**迁移已有工作：** 保留已有入站事务、时钟、话题隔离、并发上限与 outbox 工作，但按新的事件/行动语义重新验证。迁移方案如下，实施前仍须针对真实旧数据库和崩溃点测试：

- 单活进程停止新旧调度交接，先在持久库标记迁移版本与各话题切换位点；旧历史仅作为新工作单元的上下文，不把已处理的全部历史重新当成新事件。原先未处理的消息按稳定事件 ID 导入新队列。
- 旧 `sent` 和 `failed` 保持历史；旧 `unknown` 保持未知，旧 `sending` 恢复为 `unknown`，均不自动重发。结果作为历史事实或不确定观察供 Agent 使用。
- 旧 `pending` 标记 `origin=legacy`，只按旧恢复协议完成已持久意图：授权有效、原意图未过期、同话题没有使其失效的新消息且版本检查通过时可领取，否则记录未执行原因并将结果提供给新 Agent。它不冒充新 Agent 的自主决策；新收到的事件不再进入旧策略。此选择保留先前已生成待发送意图的恢复行为，不是对新消息重启旧策略。
- 旧决策尚未产生发送意图时，不自动把它转换成发言；其未决事件交给新工作单元自主重新观察。无法判明状态或归属的记录显式隔离，既不静默丢失，也不自动发送。迁移标记、旧新位点、行动 ID 及记录映射应幂等，重复重启不得重复迁移或发送。

当前阶段一工作树尚未提交，测试结果也不能直接证明本设计已实现。

## 具体行为示例

1. 群里无人 @ Bot，两个人说服务内存飙升，第三个人提供新版本部署时间。一次合批后，Agent 看见事件和此前状态，发现自己能提出一个尚未讨论的可验证检查，于同一个自主工作单元调用 `send_message`；也可以判断信息不足并等待。是否真的能稳定做到，要通过实测确认。
2. 同一场景在 Agent 唤醒前又出现“已经查到是缓存配置，修好了”。Agent 看见解决信息，可能调用 `finish_silently`。如果生成期间才收到解决信息，严格新鲜度模式会把它反馈给 Agent；有界模式可能允许在尚未看到它时发送，因此需要衡量过时发言。
3. 群友 @ Bot 但只是发了一串表情或重复内容。调度器可以更快唤醒；Agent 根据上下文选择沉默、简短回应或澄清，而不是由提及规则强制回复。
4. Agent 发现问题可能稍后才有结果，登记“等待该话题的新事件，最晚十分钟后再观察”。中途有新消息或到期时再判断；如果群友已解决，取消等待，不发过时追问。

下面是一段示意轨迹，名称和结构不是现有接口：

```text
workflow-42 输入：events=[“内存上涨”, “刚发布了新版本”]，没有 @
Agent：update_state(关注这次内存问题，关联原事件)
Agent：send_message(“可以先对照新旧版本的内存限制和缓存配置。”)
执行器：action-7 已持久接收；随后记录 sent / failed / unknown

workflow-43 输入：events=[“@Bot，已经找到原因并修好了”]
Agent：finish_silently()
结果：正常无发言；没有生成一条供外部决定是否发送的回复
```

这是对可追踪行为的约定，不表示模型一定会作出上述判断；质量必须通过实验评估。

## 成本与评测

合批的主要收益是减少唤醒机会，不保证 token、模型调用或费用按相同比例下降。仅作算术示意：某话题在两分钟内每秒收到一条消息，连续流量触发 15 秒最长窗口，且没有额外唤醒时，120 条事件约形成 8 个自主工作单元，而不是每条消息都单独唤醒。一个工作单元可能包含多次模型请求，真实次数还受调度、@、等待、重试和服务耗时影响。单次批次更大，摘要、状态、工具往返和重试也有成本，必须测量。

按事件、工作单元、Core activation、行动、群和话题关联统计：输入/输出 token、provider 实际提供的缓存读取和推理 token、调用次数、重试、费用或注明单价的估算；缺失 usage 标记为缺失，不能记作零。记录每千条已接收事件、每个活跃群每天、每次有用介入的成本，同时记录接收至唤醒及实际送达延迟、预算延迟、队列长度、上下文压缩和未知送达。空结果、失败和不发言的调用同样计入分母。

使用相同事件流、模型、预算和提示词版本，对照当前规则方案、只响应明确提及、外部分流加生成、以及目标自主循环；样本顺序和实验条件预先固定。评价应包含真实本地模型与假平台可控故障两类，先做离线可复现回放，再做用户授权的真实群聊观测。至少覆盖：

- 无 @ 时有人未解决问题与已经解决的配对场景，分别衡量有用介入和打扰；被 @ 但没有回应价值的场景，验证不被强制发言。
- 状态和等待的跨重启延续；定时器到期前问题已解决、等待过期和恢复后延迟。
- 生成中新增消息、编辑、跨话题并发、同话题顺序、决策/领取竞争、崩溃恢复及结果未知；用真实子进程退出测试持久边界。
- 外部调度暂停或预算不足、模型空响应、模型明确 no-action、工具拒绝和发送未知：逐类归因且不混计。
- 无 @ 低频群的最长排队时间与高流量持续输入下的进展；记录被压缩、呈现、延迟或未处理的事件，检查是否静默遗漏。
- 在不告知方案身份的情况下，以完整对话让人评估帮助程度、打扰、过时发言和自然度；同时报告样本数、失败与成本，不能挑选示例证明自治。

核心验收不是固定回复率：必须能追溯已接收事件是否真正呈现给 Agent，看到同一个自主工作单元选择工具或明确 no-action，并观察它随上下文变化而改变行为。真实 Telegram 交付权限、目标模型的工具调用兼容性、自治质量、预算和稳定性均尚未验证。

### 实现记录（同日晚间）

已按本文实现，改动分两个仓库：

**Core（Nervipulsa）** — 通用、与 Telegram 无关的三处扩展：

**App（本仓库）** — 自主循环：
