# 长对话实验：脚本群聊的吞吐与缓存

日期：2026-10-27
模型：`opencode-go/muse-spark-1.3-contributor`（本地 Magpie，`http://127.0.0.1:3425/v1`）
脚本：`experiments/long_conversation.py`
原始数据：`docs/evaluations/long-conversation-2026-10-27.json`

## 这是什么，不是什么

**是**：49 轮脚本化群聊，5 个化名成员（alice / bob / carol / dave / erin），10 个连续话题段落，跑真实
Nervipulsa Runtime + 真实模型。Telegram 是录制替身，什么都没发出去。

**不是**：真人测试。群友的话是我写的脚本，所以"自然度"只能看机器人的**回应**是否接得住，
不能据此推断它对随机插话的反应。这一点在 `HUMAN_NATURALNESS.md` 里已单独界定。

## 会话结构

十个段落故意覆盖不同压力：

| 段落 | 内容 | 考察点 |
| --- | --- | --- |
| 1 | deploy OOMKilled，回滚 | 被点名后给可用答案 |
| 2 | billing 少 8%，kafka lag | 换话题、换说话人 |
| 3 | "他说的对吗" | 追认前文 |
| 4 | 周末看展 | 闲谈时**不该**插嘴 |
| 5 | `EXPIRE key 0` 错误前提 | 敢不敢纠正 |
| 6 | CronJob 时区，spec.timeZone 未填 | 有边界感的正确答案 |
| 7 | "你是真人还是机器人" | 身份透明 |
| 8 | 重放补 ledger，幂等 | 隔了十几轮后的话题回归 |
| 9 | 中午吃什么 | 又一段闲谈 |
| 10 | "今天这几个事你都跟下来了吗" | 长上下文归纳 |

## 结果

```
49 轮
  39 轮沉默（proactive 关，未被点名）
  10 轮决定回复
     8 条真正发出
     2 条模型给了 token 但没有可用内容（见下）

token
  prompt     28,823
  cached     22,250  → 缓存命中 77.2%
  completion 14,119
  reasoning  13,821  → 占输出 97.9%

延迟（10 次回复决策）
  平均 10.53s / p50 8.93s / p90 11.52s / 最大 28.92s
  实际发出速率 4.56 条/分钟
```

### 缓存命中随轮次变化

`cached_tokens` 随轮次增长而分化，不是恒定比例：

| 轮次 | prompt | cached | 命中 |
| --- | --- | --- | --- |
| 7 | 1244 | 1137 | 91% |
| 15 | 1758 | 1393 | 79% |
| 22 | 2211 | 1649 | 75% |
| 28 | 2591 | 2161 | 83% |
| 35 | 3913 | **1137** | **29%** |
| 41 | 4347 | 3825 | 88% |
| 48 | 4801 | 4337 | 90% |

第 35 轮降到 29%，该轮问题是「你是真人还是机器人」。历史记录没有保存完整请求
payload，因此无法判断前缀是否变化、哪些部分命中，或缓存是否被淘汰。要研究机制，
需要保存并比较相邻请求的完整消息序列，同时结合服务商的缓存行为。

本次汇总中 prompt 为 28,823 token，报告的 cached 为 22,250，两者差值为 6,573。
这是用量字段的算术差，不是账单金额或可直接认定的计费 token；实际计费取决于
服务商的规则和价格。

### 推理 token 吃掉了输出预算

13,821 / 14,119 = 97.9% 的输出 token 被报告为 reasoning。两次回复无可用内容：

| 轮次 | completion | reasoning | 结果 |
| --- | --- | --- | --- |
| 9 | 1511 | 1496 | `response_invalid`，无内容 |
| 22 | **4096** | **4094** | 撞到 `max_output_tokens` 上限，无内容 |

第 22 轮达到 4096 上限且 `content` 为空；第 9 轮没有达到上限，空回复原因未确定。
这一观察说明输出预算可能影响结果，但不能把两次空回复都归因于触顶。

旧版 JSON 的 `invalid_model_responses` 与 `empty_model_responses` 计数使用了策略原因字段，
不能可靠反映模型结果；原始记录里索引 9 和 22 的 `turn_outcome` 均为 `error`。
旧 JSON 没有保留每个错误的 `error_kind`，因此不能仅凭该 JSON 重算具体错误类别。
其中 `model_calls_billed` 实际按非零 usage 计数，也不能证明计费。新版实验脚本已修正口径；
历史 `docs/evaluations/` 中的 JSON 和聊天记录原件保留，没有重新生成。

**已修正并复测**：应用默认预算改为 `max_output_tokens = 1000000` / `context_limit = 1000000`
（此前分别为 4096 token / 40000 字符），`request_timeout` 提高到 900s。
`context_limit` 是 Core 序列化模型视图的字符预算；`max_output_tokens` 是有限的输出
token 上限，provider 还可能施加自己的限制。

同脚本、同台词复测（`long-conversation-1m-2026-10-28.json`）：

| | 旧预算 4096 | 新预算 1M |
| --- | --- | --- |
| 决定回复 | 10 | 9 |
| 实际发出 | 8 | **9** |
| 模型给了 token 但无内容 | **2** | **0** |
| 延迟 均值 / p50 / p90 / 最大 | 10.53 / 8.93 / 11.52 / 28.92 s | **8.23 / 7.30 / 11.59 / 14.21 s** |
| 发出速率 | 4.56 条/分钟 | **7.29 条/分钟** |
| prompt 总 | 28,823 | 25,082 |
| 缓存命中 | 77.2% | 68.9% |
| 推理占输出 | 97.9% | 97.1% |

此次复测的 9 次回复均有内容，不能据此断言所有截断已经消失。
两次「决定回复」从 10 变成 9：逐项比较 JSON 中的决策（索引从 0 开始），
差异出现在索引 9，旧运行将该条判断为点名，新运行判断为沉默。索引 22 两次都
决定回复：旧运行 4096 completion tokens 后无内容，新运行使用 1963 completion
tokens 并给出追问。台词相同并不意味着策略和模型输出完全相同，不能单独归因于预算。

表中的发出速率以成功发送数除以回复决策耗时之和计算，是这次串行实验的指标，
不是并发吞吐量，也不是整段群聊墙钟时间内的发送速率。

另外，新预算下第 48 轮的 `cached_tokens` 是 0（命中率拉低了整体数字）。这一轮问的是
「今天这几个事你都跟下来了吗」，需要跨全部话题归纳。缓存从 88.9% 降至零是观察到的
现象；由于没有保存完整请求 payload，不能断言前缀变化或缓存淘汰。旧预算那次也
观察到下降至 29%。

## 这轮实验发现的两个真实缺陷

### 1. 一次空回复让会话永久卡死（Core）

第一次跑到 49 轮时出现了离奇现象：10 次模型调用 `prompt_tokens` 全部相同（1485），
6 条回复逐字节相同。根因在 `LLMActor`：

- 空回复 → `response_invalid` → pause
- 新用户消息到达 → 被 `_held` 挂起，**不投影**
- 恢复时重试的是**冻结的旧快照**

于是每一轮都重发同一个旧请求，看起来在工作，实际什么都没推进。

修复：`response_invalid` 遇到新的 `user.message` 时清除 pause，让挂起的消息
进入新的 activation。操作员主动 `retry` 仍然重试冻结快照（这是对的——重试就该是
同一个请求）。回归测试：`tests/test_response_invalid_recovery.py`（3 个用例）。

### 2. 成功回复的 token 用量从未落库（应用）

`_process_turn` 只在失败分支写带 usage 的 decision 行；成功回复写的是模型调用**之前**
的那一行，只有 trigger。后果：任何按 usage 做的成本统计都只能看到失败，看不到成功。

修复：`store.update_decision_detail()` + 在拿到 activation 后回写。没有这个修复，
本文所有 token 数字都拿不到。

## 关于测量本身的一个教训

第一版脚本取「transport 里最后一条发送」作为本轮回复文本。当某一轮超时（没发送）时，
它会继承上一轮的文本，于是报告里出现了「6 条重复回复」——那其实是脚本的 bug，
不是模型的行为。现在回复文本只从 `sends` 表里按 `decision_id` 取，没有发送就是空。

同样地，`model_calls` 一开始按「有 token 用量」统计，会把失败和超时排除掉，
等于把出问题的轮次从平均值里删掉。现在按「是否真的发起了回复决策」统计，
失败单独记 `send_failures` / `replies_withheld` / `invalid_model_responses`。

## 结论

- 长会话是可用的：49 轮、10 个话题，机器人跟住了 deploy、billing、cron、redis 四件事，
  最后一段归纳点名了正确的事项。
- 闲谈段落（4、9）它全程沉默，这是对的。
- 报告的缓存命中率为 68.9–77.2%，个别轮次降至 0% / 29%；原因和计费影响未确定。
- 旧 4096 上限下 10 次决策有 2 次空内容，仅一次达到上限；新默认值下 9 次决策均
  成功。这些样本不能估计失败率，也不能证明 1M 消除所有截断。
- 两次运行的最大延迟分别为 28.92s 和 14.21s；决策次数和结果不同，不能归因于
  预算调整。

## 没做的事

- 没有连真实 Telegram API，没有向任何群发消息。
- 没有测并发：整个实验是单话题、单 runtime、串行轮次。多话题并发下的吞吐未测。
- 群友台词是脚本，不是真人；"自然"的结论只覆盖对本脚本的回应质量。
- 缓存掉到 0% / 29% 的机制没有被直接观测，历史记录没有保存完整请求 payload。

## 测试状态与一个已知的不稳定

应用：`141 passed`。
Core：`175 passed`，`tests/test_crash_boundaries.py` 有 3 个用例会间歇性失败。

这个失败与本轮改动无关，已在**干净基线**（`git stash` 后）复现：连续三次运行分别是
`1 failed`、`3 failed`、`1 failed`，且每次挂的用例不同。失败形态是子进程写出的 JSON
文件在被读取时还是空的——是 Windows 上崩溃边界测试的时序竞争，不是逻辑错误。

顺带修了同一个文件里一个真实的 teardown 缺陷：`_kill_tree(restart)` 少传了必需的
`worker_pid` 参数，会让 teardown 抛 `TypeError` 掩盖真正的断言结果。
