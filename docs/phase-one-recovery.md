# Phase one recovery boundaries

Inbound update and message are committed together. Debounce uses the turn manager's monotonic clock; SQLite timestamps are wall-clock seconds. On startup, undecided messages are regrouped, and an already opened but undecided turn keeps its original identity and message range. A reply decision with no prepared send is regenerated from its saved decision and messages.

A pending send has not been claimed and can be resumed only if its decision remains current, its chat is authorized, it is less than 24 hours old, and no newer inbound message exists in the same topic. Obsolete pending sends become failed. The claim checks the decision and freshness in the same SQLite write as the pending-to-sending transition. A sending record left by a terminated process becomes unknown and is never retried automatically: Telegram may already have accepted it. A confirmed send, its turn closure and its locally recorded message commit together. A crash after the remote service accepts a message but before this transaction commits remains unknown; exactly-once remote delivery cannot be guaranteed without a Telegram idempotency key.

Live polling schedules turns independently; a per-topic lock preserves order and a four-slot semaphore bounds concurrent model work. In-memory queued work is reconstructed from the durable inbox on restart. The application assumes a single active process per database: startup orphan recovery is not a distributed lease and must not run concurrently with another live instance. Offline tests use fake transports and agents, not a real Telegram service or model.
